## Audit findings (source-of-truth, not assumptions)

- **Lobby vehicle state:** `QueryLobbySessionPolicy()` deliberately sets `PhysicsSimulated=false` and `EquilibriumPlacement=false`; `Lobby.levelspace` agrees. The visible hero is therefore rendered as a resting vehicle, not advanced by vehicle physics. Proving Ground enables both flags. The existing `PhysicsVehicle::ResolveEquilibriumPose()` performs four-wheel ground probing and accounts for wheel/suspension geometry, tyre radius and static deflection when physics placement is enabled.
- **Lobby vertical placement:** decoded `Lobby.facetspace` shows the studio floor top at about Z=0.009 m; the original hero body is at Z=0.53 m and the four wheel centres at Z=0.50855 m (tyre bottoms approximately Z=0). `Lobby.levelspace`’s vehicle ground anchor is Z=0, so raising the whole vehicle would lift its tyres off the floor. The archived body/COM interpretation is still unconfirmed; do not change the ground anchor blindly. A shared `Vehicle::ResolveRestingHubLocal()` now resolves wheel mounts plus static strut compression and is used by `PhysicsVehicle::ResolveEquilibriumPose()`, the parked/editor vehicle visual, and both editor/runtime camera-subject fallbacks. Static visuals now derive the chassis COM from tyre radius, mean tyre deflection and mean resting hub, then convert COM to the authored body origin; wheel visuals come from the resolved suspension hubs. A C++ regression checks the authored socket/rest-hub identity and body-clearance equation under changed radius, mass split and strut rates. Native builds and focused tests pass, but the Lobby body/COM meaning and actual viewport clearance still need a fresh native runtime inspection/capture. Keep Lobby parked/static unless evidence supports active simulation.
- **Transform gizmo:** the viewport’s shared spatial-gizmo path now accepts a visible, selected `VehicleRecord`’s `VehicleConfiguration::Spatial` when physics is stopped; move/rotate/scale mode keys, drag and cancel all use the existing gizmo and revision path. Vehicle handles remain disabled while physics owns the live transform. Native editor builds pass; actual selectable/visible behavior still needs an in-app check.
- **HMI:** there is no per-level HMI field in the two level records. “HMI” currently names a vehicle-camera rig that frames the centre-console tablet. Lobby already exposes that rig in Game-camera mode; an added direct HMI toolbar action is shown when a vehicle camera subject exists, including the Editor-camera path used by Proving Ground. Do not invent a persisted HMI flag. Confirm both levels’ actual subject/tablet framing in the native runtime.
- **Tyre smoke / plume:** native `PlumeSourceProjector::ProjectVehicle()` already gates contact-patch smoke on wheel contact/load and filtered slip (slip ratio, slip angle, slip velocity or dissipated sliding power). It also emits a short smoothed decay after slip ceases. Add explicit zero-slip/no-contact and slip/skid-positive C++ validations; if a real run still smokes continuously, trace the live telemetry that crosses the gate before changing thresholds.
- **Plume implementation:** `PlumeSourceProjection.cpp` is native C++ source projection; `PlumeSpace.cpp`/`PlumeLayouts.slang` provide the GPU plume transport/raymarch. Validate these paths and their coupling directly in C++/GPU tests, not against the HTML prototype. Existing Fluid Dynamics validation is not an end-to-end flipbook/warm-up export test.
- **Collision:** native Jolt/vehicle physics and geometry collision are independent of fracture. Verify a dynamic, non-fracture cone/object receives a collision impulse and remains usable with fracture disabled. Do not require destruction for ordinary collision response.
- **Native and Experimental editors:** the accepted Fluid Editor remains modal and is explicitly out of scope for redesign or migration. Particle and Fracture now use normal in-app dockable ImGui windows, while ForceField/Wind has an opt-in dockable workbench; their C++ code now compiles in the host verification builds, but none of the windows has been visually checked. The native Fracture canvas now generates deterministic clipped Voronoi convex cells with paired cut-face tokens and a checked volume summary, but it is author-time preview geometry only—not a runtime stress solver, debris simulation, or Jolt collision bake. ForceField already has a contribution-grouped source list that selects individual records, a per-source inspector, and viewport timeline lanes with per-trigger Fire actions; its visualization includes map/oblique/camera projections. The remaining ForceField/Wind implementation needs the pending verification. `Experimental/` includes Fluid, ForceField, Particle, and Fracture editor prototypes; these are not standalone native capabilities.
- **Authoring access:** `EverestWorkspace`’s constructible/visible type list omitted native `FluidPlume`, `Fracture`, and `Particles` records even though `WorldSpace` registers them and inspectors exist. These types are now added to the native Construct/Outliner catalogue; record creation, persistence, editor launch and runtime effect still need verification.
- **Vehicle inspectors/workspace:** Batch 5 now extracts a reusable bounded curve editor, migrates the Vehicle inspector to it, and provides version-1 `.vcurves` TOML import/export with finite/order/domain checks and transactional partial overrides. The Vehicle Workbench now exposes vehicle quick configuration, linked child Tyre inspection, telemetry and test/reset flow. Vehicle reset uses the existing physics reset command path. These paths compile; native Vehicle Workbench interaction remains unverified. The collision-driven particle streaks have now been visually checked in the native offscreen viewport. The separate derez-effect audit remains a VFX follow-up, not part of the verified Batch 5 curve/impact scope.
- **Camera ownership/switching:** `SceneViewportNavigation`/`SceneViewportFlight` own editor navigation; `VehicleCameraSolver` owns the driven/cinematic rig. The existing toolbar already had a two-domain selector (renamed from Editor/Game to Editor/Vehicle). The former mode switch replaced the editor `Flight` with the vehicle pose and returned in Free mode; it now snapshots/restores the complete editor flight/navigation state, including the Space-view bookmark, without resetting the vehicle rig. `EverestInterfaceValidation` exercises the round trip; live toolbar/mouse interaction remains unverified. No native `CameraRecord`/`CameraConfiguration`/codec exists: `RecordClassification::Camera` is a category label, and `VehicleConfiguration::ChaseCamera` is only a follow toggle. `SceneViewportRequest` carries pose, vertical FOV and near clip; panel dimensions determine aspect, while authorable far clip/sensor fit/focus are absent.
- **Camera effects/post-processing:** `OpticalFlareRecord` remains a separate environment record, not nested in `SolarRecord`; `EnvironmentOverlay` maps its settings onto a `RealmSolarSource`, which remains the renderer’s flare source. `CameraShakeComponent` is now an engine-side, seeded velocity/impact component owned by `VehicleCameraSolver`; it is enabled by default, uses 1.5 mm high-speed baseline amplitude and a hard 6 mm offset cap, with frequency/attack/release controls. It applies to Chase/Cockpit/Passenger/Hood rigs, not Editor/Orbit/HMI/tyre views. `CameraMotionBlurComponent` has exactly three native dropdown choices—Off, Camera only, Full scene (camera + objects)—and is Off by default. `SurfaceProjection::MotionView` now carries total motion in RG and camera-only motion in BA; temporal AA continues using RG, while the current-frame five-tap blur caps motion at 24 px. A SwiftShader A/B capture verified both enabled modes. The popup settings are per-workspace camera state and are not yet persisted because no native `CameraRecord`/codec exists. Reference audit: Slate’s pinned C++ `CameraComponent`/`CameraProjection` are host-owned pose/projection classes using Y-up and millimetres; the Frontier- `CameraInspectorPanel`/`CameraOptics` is an optical study and explicitly does not persist settings or switch cameras. The upstream repos report no declared license, so no source was copied; only high-level behavior is retained as guidance.
- **Fracture reference:** fetched `https://github.com/c7egoist/Frontier/tree/arena%2Feb353da2-frontier` without checking out or switching branches (`FETCH_HEAD` = `acb0502`). Its design doc and JS describe a flat-convex runtime clip/bond pipeline and a substantially more ambitious engineering bake. The fetched tree has no top-level `LICENSE`; do not copy source files or wholesale-merge it without an explicit license review. High-level methods can guide an independent implementation, but design-doc performance claims are not validation. The native independent Voronoi clipping core added in the current workspace is not yet either reference pipeline and is not a runtime fracture solver.
- **Composition paths:** ParticleEditor gets the level field through `InspectorRuntime::LevelFlowSampler` → Everest's `SampleLevelFlow()` → `ConfigureAtmosphericFlow()` / `ForceFieldSpace::EvaluateWorldFlow()`. `ParticleEditorWorkspace::Present()` samples the authored level anchor, transforms the axes into particle-domain coordinates, and `ParticleSpace::Advance()` appends the sampled flow only when `LevelWind.Follow` is enabled; `.particlespace` stores the follow flag and anchor, not a stale sampled vector. Separately, `RenderingExtension::SynchronizePlumeSources()` maps an enabled `WindRecord` with `AdvectPlumes` into `PlumeSettings::WindVector`, which `PlumeSpace` uses for plume transport. The Fluid Editor's `.fluidspace` simulation remains separate; keep these as explicit inputs, not one merged solver.
- **Particle/VFX inventory:** native `ParticleLibrary.toml` contains 52 presets, including `derez-cube`, `black-hole`, and lightning effects. Check runtime reachability/rendering and compare with the Experimental list; do not recreate presets already present.
- **Particle physics reference:** the selectively fetched `c7egoist/Frontier` branch `arena/eb353da2-frontier` resolves to `acb0502` and contains the fracture/sun/atmosphere/cloud workspace, not a Particle physics implementation. No Particle algorithm source was found there; keep the user's separate Particle-branch reference unresolved and do not substitute the fracture branch or wholesale-merge either source.
